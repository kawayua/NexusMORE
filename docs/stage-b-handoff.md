# 阶段 B 交接：契约与人工确认

入口条件：2024年A题问题1已获得可追溯的成功运行与失败记录，用户接受参考差异。阶段A结论和统计见[验收小结](../stage-a/2024-A-problem-1/stage-a-summary.md)。本文件是待实施设计，不表示Schema、数据库或恢复功能已完成。

## 从实际失败反推契约

| 阶段A证据 | 应写入的契约/工件 | 如何核验 |
|---|---|---|
| 0.55 m误作龙头孔距 | 原始尺寸、单位、派生孔距、推导关系和题面出处 | 单位归一化；人工核对3.41−2×0.275=2.86 |
| 用固定弧长代替刚性直线约束 | 变量、几何约束表达式、物理含义、可计算残差 | 检查实际直线距离，不能只检查模型自定义弧长 |
| 盘入方向和前后顺序错误 | 坐标系、初始状态、方向约定、节点顺序、选根规则 | 初始坐标、极角随时间变化、节点排序 |
| 速度公式与轨迹不一致 | 速度矢量/速率定义、推导关系、独立检查方法 | 连接约束求导与时间差分对照 |
| 输出截断 | 调用元数据与失败类型，不塞入数学契约 | 保存finish_reason、原始响应和usage；拒收不完整工件 |
| Excel精度要求 | 输入输出schema、模板哈希、数组形状、字段单位、数值和显示精度 | 完整性、回读、舍入和number_format |
| 方案写RK4、代码改为弧长求根 | 允许的方法变化范围、契约版本、实现差异说明 | 若改变被确认的硬性要求则新版本重确认；仅等价实现按既定规则审阅并记录 |
| Windows换行哈希差异 | 原始字节哈希、规范化策略与代码审阅绑定 | 不能以规范化为由忽略实际代码变更 |

建议数学契约字段族：问题范围与题面引用、输入清单、单位和坐标约定、参数与派生关系、变量、假设、目标、约束、求解方法、输入输出schema、检查项、已知风险和备选。目标字段要支持simulation，不强迫所有题都有优化目标函数。

版本ID、确认、run_id、工具配置、审阅哈希及调用统计作为关联业务工件保存，与数学内容分清职责。题面事实、假设、参考对照分别标记来源；参考答案不能静默流入独立生成。

## 第一条实施链

先编写版本化Model Contract的JSON Schema、字段说明，以及本题合法/不合法样例。为关键检查项分配稳定ID，写明判定方式和passed/failed/unknown；JSON结构合法不意味着物理或数学合理。

随后设计PostgreSQL业务记录：项目、小题、契约版本、用户指导、两类确认、运行及产物元数据；执行必须绑定已确认版本与输入快照。用迁移管理结构，版本不可静默覆盖。

再把现有串行节点接入LangGraph，明确两个等待点：方案待确认和结果待确认。最小CLI应支持查看、确认、拒绝及要求修改。真实LLM接入保留接口，但状态流测试优先使用固定工件，避免为测试恢复反复消费API。

最后接入PostgreSQL checkpointer并演练重启恢复，建立业务记录与checkpoint的幂等更新及核对机制。不假设两者天然原子一致。继续使用已有经审阅Docker执行接口，不在B阶段提前重写MCP服务。

## 必须验证的状态规则

- 没有用户确认不能求解；未确认结果不能写论文。确认必须绑定小题、具体版本和用户动作，Agent不能代确认。
- 重复确认不重复求解；过期版本确认不能推进当前状态；拒绝保存原因并保持待处理。
- 用户修改模型、输入或硬性方法要求：产生新版本，重新确认，使下游代码/结果失效；保留历史。
- 仅修改解释：保留计算产物，重做必要审核、结果确认和文字，不自动重算。
- 重启后分别恢复到方案和结果等待点；业务记录与checkpoint不一致时能核对和修复，不误推进。
- 任何待确认版本与代码、执行、结果、确认之间有可查关联。契约检查允许unknown，不强制模型编造通过证据。

阶段B验收演示：初稿→用户补充→新版本→确认→求解→结果确认，并演示重复/过期确认与两个等待点的服务重启。暂不建设复杂前端、并发角色、大规模RAG或MCP服务。
