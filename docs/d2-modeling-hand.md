# D2 建模手与独立 M1

D2 将建模手的拆题、资料选择、方法适配、数学说明、修改讨论接入现有任务；程序负责版本和持久化，独立 Validator 负责 M1。代码手、P1/P2 和论文手仍在后续阶段。

## 入口与流程

```powershell
python -m modelcrew init-db
python -m modelcrew modeling-run <task> --version <current-version> --guidance-file <utf8-guidance.txt> --actor <operator> --request-id <unique-id>
python -m modelcrew modeling-status <task>
```

API 为 `POST /tasks/{task_id}/modeling/runs`，请求字段为 version、guidance、actor、request_id、auto_correct；`GET /tasks/{task_id}/modeling` 查看历史、状态和证据位置。入口会产生配置模型的实际费用。状态查询、任务恢复和重复同一请求不会自动重发模型调用。请求是同步长调用，但运行状态在 PostgreSQL 中逐步保存，可从另一个请求查询。

首版要求任务处于 WAITING_MODEL_APPROVAL、有已验证结构的契约及 B+ 数学基线；已批准的方案须先显式创建新版本。它能使用参考辅助的现有基线修订，不是从任意自然语言题目自动建立数学包的通用系统。

流程如下：

1. 读取并核对原始输入文件字节，提取实际题面/结构；缺失或变化时阻断。保存原始证据、基线版本及暴露说明。
2. 建模手先拆解当前小题、选择资料类别和真实卡片 ID；检查任务图无重名、未知依赖或环。此图是当前小题内部工作项，不创建/调度第二小题。
3. 程序经 D1 能力检查，先读算法索引，再按需读取现有 C+ 卡片原文。保存位置/哈希/版本、条件未知项和未覆盖情况。这里接入本地条件化卡片工具；既有 MCP 检索/来源 API 继续可用，本轮没有新增自动联网搜索规划。
4. 建模手根据原题、基线、资料和指导输出方法/数学包的 JSON 修改、引用采纳或拒绝及适配局限、中文方案和待澄清问题。完整契约/数学 Schema 进入模型请求；资料内容没有工具授权。
5. 确定性检查通过后，调用已有 revise_model / revise_mathematics 保存新版本；若仅展示变化则调用已有数学展示更新。给定事实、输入/来源、参数/单位和已有检查不可静默改写。原版本/确认留存，所有新检查仍 unknown。
6. 程序冻结 D1 快照，登记作者，创建新质检身份和 M1 票据。Validator 使用独立、无作者聊天历史、无写入工具的请求，读取原始证据、契约、数学包、来源与方案，逐项审核 M1。
7. 审核证据必须引用快照中存在的 artifact_id 和可解析 JSON Pointer；D1 进一步校验完整性、身份、政策及逐项/总状态。语义是否正确仍由独立审查判断，指针存在不等于论证成立。
8. M1 PASS 且无开放问题时进入 ready，仍等待用户确认。FAIL 回建模手，结构修复和 M1 触发修订共享最多一次自动返工；耗尽为 needs_human。BLOCKED 或待澄清问题不自动猜测，保持 blocked。服务异常/未知响应单独保存，不当作代码失败或盲目重发。

“一个建模手”表示一个业务职责主体，可有分步骤调用。规划结果和来源以结构化工件交接；每个新方案版本用新的调用上下文，不用同一作者上下文切换身份做审查。M1 同供应商调用仅表示上下文隔离，不能保证统计独立或数学正确。

## 与用户确认和执行绑定

迁移 008 增加 mc_modeling_runs 与不可变 mc_modeling_events。只有实际调用过 D2 的任务才受新 M1 门禁约束，历史任务的 unknown 审核和原确认保持原适用范围。

`Workflow.action(model, approve)` 在写入批准前复核最新 D2 运行、当前版本、真实契约/数学包、输入文件、D1 快照、政策和 M1 回执；批准事件绑定 modeling_snapshot。M1 无通过、过期或文件变化均拒绝。图中的 solve 和人工 solver-result 接入也重新检查，不能靠旧 checkpoint 绕过。

用户的数学语义哈希与审阅理由、引用讨论和幂等规则沿用 B/C。D2 不产生方案批准；无论模型或独立质检说“通过”，都不会自行设置 model_approved。用户反馈通过相同入口成为新运行的 guidance；实际语义变化生成新版本并重新审查，旧确认不能推进新版本。

## 可重入与权限

同一任务的建模运行持有现有任务锁，防止并发修订/批准。调用前登记请求和状态；同一 request_id 必须保持同一版本、指导和参数，只返回已保存状态，不重新调用。若进程在请求发出后中断，started/planning/modeling/reviewing 都不作为可盲目重发的授权；需要检查调用记录、原始响应和任务状态后显式处理。

所有模型调用留存去密钥的请求、响应、用量、完成/截断状态和耗时。独立质检的实际 HTTP 调用与 D1 派发身份有明确映射。模型没有业务确认/数据库写入/执行工具，所有 JSON 修改由程序校验后应用。作者/审查独立性基于本程序创建的无历史请求，不声称可审计供应商内部状态。

## 实测与边界

本地结构/流程测试使用明确标记的 FixtureModel；其指导和批准是模拟输入，不能算用户真实确认。真实验证使用独立 stage-d2-development 项目和已有板凳龙基线，指导由验证者构造，明确不是用户对正式模型的指导或批准。该验证不触碰已确认论文，也不执行新求解。

真实验证入口：

```powershell
python -m scripts.verify_d2_modeling --task <new-development-task> --request-id <unique-id>
```

具体运行结果、所有失败尝试及最新证据见 [D2 工程报告](../stage-d/d2/acceptance-report.md)。能力评价仅限本次固定回归题；跨结构建模质量、多小题依赖调度、代码执行和论文写作分别在后续阶段验证。


## 只读质检复核与总状态

独立质检也可能误报。`POST /tasks/{task_id}/modeling/{run_id}/recheck` 接收 version、actor、request_id、rationale；CLI 为 `modeling-recheck`，另传 `--run-id`、`--rationale-file`。仅允许最新、未批准、产物和原始输入字节未变且已有 FAIL 的运行；每个运行最多一次显式只读复核。不调用建模手、不改模型、不增加作者返工预算。原始 FAIL、挑战理由、独立复核原文和两个回执全部保留，复核继续失败仍阻断。此入口不是跳过 M1 的批准开关。

逐项语义检查由 Validator 给出；顶层总状态是机械汇总，由程序按 FAIL→BLOCKED→PASS 优先级生成。旧格式允许模型返回顶层 status，但仅作为原始建议保留；不一致时在 admission.json 记录 reported_status、derived_status、aggregation_mismatch，绝不改写逐项结论、问题或证据。缺必查项、无证据、无效指针或未解决严重问题仍不能通过 D1 准入。这样可避免复制旧总状态导致“六项均通过、无问题、却总 FAIL”的格式矛盾，也不能用顶层 PASS 覆盖任何逐项 FAIL。

复核响应已完整保存、但程序在准入前中断时，相同请求可以重新验证缓存、派发票据、当前版本、原始输入和快照；不再调用模型。缓存不完整或派发不唯一则拒绝，不以未知状态作为重发授权。

实际演示中，首次 M1 将 m² 与 m² 误认为量纲矛盾；只读复核明确撤回该意见，六项均给出 PASS，但保留了顶层 FAIL。程序保留原文并按真实逐项结果汇总，未改数学公式。所有失败和截断尝试纳入报告，不把单题通过解释为通用数学正确性保证。
