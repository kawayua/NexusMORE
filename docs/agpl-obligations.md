# PyMuPDF／MuPDF 的 AGPL 义务核对

2026-11-14：已核对固定 PyMuPDF 1.27.2.3 的官方源码、PyPI 文件摘要、MuPDF 1.27.2 许可和 Artifex 官方说明。结论是：可以继续按开源许可使用，不必仅因使用它就购买商业授权；但对当前同进程调用 PyMuPDF 的枢模发行，不能把“原创文件采用 Apache-2.0”解释为组合产品仅需遵守 Apache。**本批完成条款与缺口核对，尚未完成组合发行的 AGPL 落实，也没有公开发布。**

## 范围与依据

当前 pdf_checks、paper_render、paper_layout、paper_export 直接 import fitz，参与同一论文导出/校验流程；不是已证明独立的简单软件聚合。发行准备按受 AGPL 覆盖的组合程序处理，不以独立 pip 下载、动态导入或名称更改为免责依据。AGPL 第 5 条规定受覆盖组合的整体许可条件，第 13 条还允许 AGPL 与 GPLv3 部分组合。具体纳入范围须按代码与依赖的实际关系列明，不把所有同仓库文件无差别纳入。

原文 [AGPL v3](licenses/AGPL-3.0.txt)来自 SHA256 核验的固定源码包，保持字节不变；[固定版本 COPYING](https://github.com/pymupdf/PyMuPDF/blob/bf51516c1b1146d357e3705473f7dea6a405a589/COPYING)、[PyPI 1.27.2.3](https://pypi.org/project/PyMuPDF/1.27.2.3/)、[Artifex 许可说明](https://artifex.com/licensing/)、[MuPDF 1.27.2 COPYING](https://github.com/ArtifexSoftware/mupdf/blob/1.27.2/COPYING)均有本地来源/哈希证据。GNU 官网直取遭遇 TLS 失败、ReadTheDocs 返回 429，未把失败页面当作已读；采用固定发行源码内的完整原文核对。

已安装 wheel 的 COPYING 只有一行“双许可”说明，不能替代完整文本。源码包含完整 AGPL；同时 src/__init__.py 头部标 GPL-3.0-only，MuPDF README 标 AGPLv3-or-later。保留这些逐文件归属差异，不把元数据中的 AGPL 名称强行覆盖所有文件或宣称统一为 AGPL-only。

## 主许可证如何处理

当前根 LICENSE 仍为已确认的 Apache-2.0，适用于原创部分，第三方原许可保留。Apache-2.0 的兼容性不代表可以把 AGPL 组合改为 Apache-only。建议对含 PyMuPDF 的发行候选明确采用 AGPLv3 组合发行表述，保留原 Apache 文件归属和第三方文本，并在元数据、README、NOTICE、CLI 告知和源码说明中统一体现；若要改变项目主许可证或对原创代码增加 AGPL 授权，应另记录项目所有者的明确决定，不由这次“核对条款”自动完成。

当前准备的是 [AGPL 发行落实清单](release/agpl-obligations-review-20261114.json)，不是商用许可采购或公开发布授权。Gitee 可以作为源码提供渠道，但无须在 Gitee 办理许可证；是否公开全仓库不是唯一判断，重点是收到软件或适用网络服务的用户能按条款取得对应的完整相应源码和权利。互相独立的其他项目、用户论文和秘密不应顺便公开。

## 已查明的实际缺口

官方 PyMuPDF sdist 为 85,759,618 字节，摘要已与 PyPI 匹配；其 setup.py 明确自 2024 年起不内嵌 MuPDF 源码，而在构建时下载 MuPDF 1.27.2。**因此仅保留这个 sdist 不能宣称已有完整相应源码。** 本批只取得 MuPDF 固定版本的许可/README/提交信息，未取得并核验完整底层源码、全部第三方组件或在 Windows 重建原生 wheel。

此外，完整 AGPL 文本已保存供核对，但尚未装入新的发行包；项目仍需组合许可决定、逐项组件告知、对应源码与构建材料、实际源码获取入口及有关安装/网络场景检查，才可把 AGPL 发行准备登记为通过。旧 F4/F5 冻结记录和当前主 LICENSE 未改写。
