## 三个主 Agent 如何分工

| 主 Agent | 内部职责标签 | 主要输入 | 权威交付物 |
|---|---|---|---|
| 建模手 modeling | Planner + Researcher + Modeler | 原题与附件、用户目标/指导、依赖已满足的上题结果 | 小题依赖图、按需检索与来源采纳记录、方法比较、版本化契约及数学说明 |
| 代码手 coding | Coder | 已确认且通过模型审查的契约、冻结输入、必要算法/接口资料 | 代码、最小运行入口、真实执行回执、全量结果、候选图和复现清单 |
| 论文手 writing | Writer | 已通过结果审查并由用户确认的结果、契约、引用、候选图 | 中文数学建模 Markdown、论断证据映射、正文/选图讨论清单及确认后的排版输入 |

建模手内部仍按拆题→先读算法索引→加载相关章节→核对条件→建立模型执行，分别保存任务、资料和建模工件；同一主 Agent 的连续工作不意味着可以省略可追溯交接。三手之间按任务、契约版本和产物哈希交接，不靠转发全部聊天历史。角色名称与模型供应商无绑定关系，三个主 Agent 可使用同一可配置模型，也不要求同时运行三个进程。

## 独立质检如何组织

Validator、Reviewer 是临时、只读的质检职责，不是第四/第五个常驻业务 Agent，也不能伪装为作者同一上下文里的“切换身份自审”。

| 检查点 | 独立审查职责 | 失败后由谁修正 |
|---|---|---|
| M1：方案提交用户前 | Validator 核对模型、假设、单位、约束、算法前提和验证计划 | 建模手修订并复验，用户最终确认方案 |
| P1：最小运行后、全量计算前 | Reviewer 核对真实执行、关键约束与输入输出 | 代码手修实现；模型问题退建模手并重新确认 |
| P2：全量结果与候选图冻结后 | Reviewer 核对结果、误差、复现和图形含义 | 按模型/实现/解释问题定向返工，再由用户确认结果 |
| W1：长篇正文前 | 未参与写作的 Reviewer 核对论断证据和大纲 | 论文手修组织，缺数值/模型依据则回对应主 Agent |
| W2：正式排版与渲染后 | 未参与写作的 Reviewer 核对中文全文、图表、引用与实际版面 | 对应主 Agent 修正，受影响项复验 |

每次独立审查使用未参与该产物编写/修正的调用上下文，输入为最小必要原始证据、验收条款和版本快照；保存作者与审查调用标识。只返回 PASS/FAIL/BLOCKED、证据、问题、返工对象和复验入口，不直接改权威代码/正文。同一审查者可延续复验，但一旦参与产物修改，就需换未参与修改的审查上下文。使用相同模型不保证错误不相关，独立上下文也不等于形式证明。没有独立调用能力时标记受限/未完成，不能把作者自检冒称独立验收。

编译、图数、哈希和数值断言等机械检查先由已有脚本处理。只有在相应审查节点才派发语义质检，不为每个函数、每张图或每段文字启动新 Agent；非必要的并行协作默认不增加。

## 阶段任务如何更新

| 阶段 | 调整后的任务与验收重点 |
|---|---|
| A+/B+/C+ | 复用已完成的算法索引、数学包、版本/确认、双 MCP、执行和中文审阅/选图/导出能力；增补主 Agent 身份与职责归属设计，不重做历史实验 |
| D1：三手交接与编排 | 定义三个主 Agent 的输入输出、工具权限和上下文范围；旧七角色仅保留职责标签；定义作者/质检身份及回执。编排器使用程序负责路由、版本、持久化和确认，不新增“总指挥 Agent” |
| D2：建模手闭环 | 在一个主 Agent 中接通拆题、索引→资料→建模→用户讨论，保存各职责工件；接 M1 独立审查，方案仍须用户确认 |
| D3：代码手最小运行 | 接生成代码、登记任务包、受控执行、P1 独立审查，未过 P1 不开展高成本全量实验 |
| D4：代码手完整结果 | 接全量计算、候选图和复现，P2 后等待用户确认；图数、证据和版本要求不降低 |
| D5：论文手审阅闭环 | 加载 writing_context，W1 后生成中文建模 Markdown，与用户分别确认正文和选图；math-reasoning 仅辅助公式，不主导论文结构 |
| D6：多小题与恢复 | 按小题/契约版本隔离三手上下文，演示等待切换、质检失败定向返工、重启恢复和过期回执拒收 |
| E：汇编与正式导出集成 | 论文手复用已批准正文和选图，接全局汇编、现有导出器及 W2；既有单题正式导出不自动算通用 E 阶段验收通过 |
| F：安装分发 | 统一安装包、依赖/资源、用户配置、干净环境部署与许可证；复用三手运行能力 |
| G：harness 接入 | 增加完整工作流MCP并在一个明确宿主真实验证；用户决定不能由模型工具调用冒充 |
| H：评测与首发 | 保留三手/契约/独立质检评测，冻结候选包做外部端到端与发布准备；七独立Agent对照可选 |

D 阶段演示必须显示三个主 Agent 的职责执行和工件交接，并至少覆盖 M1、P1/P2、W1 的审查失败/回退证据；正式排版时覆盖 W2。可用受控缺陷样例检验路由，不能强求真实业务每次都产生失败。沿用代码最多三次重试、审核触发模型回退最多一次的现有预算，耗尽转人工。基础设施故障仍走 C 的查询/恢复路径，不伪装成求解失败。

## 如何让以后任务遵循该结构

根 AGENTS.md 明确三手默认组织；resources/paper/workflow.json 的 collaboration 节记录三个主 Agent、职责映射、临时质检和当前实现边界，writing_context 每次读取本文件。这里是可加载的设计配置，不是已实现的 Agent 注册器。D1/D2 实施时应让实际工作流使用同一映射，校验审查者未参与被审产物编写，并让旧记录保持兼容，不改写旧事件或已批准论文。

修改组织职责时更新本文件、workflow.json 版本和阶段主计划；修改正文风格或图数仍分别修改 writer-instructions.md / chinese-modeling-policy.json。组织方式变化本身不修改已确认模型、结果或正文，不撤销其历史批准，也不替用户自动批准新工件。

E后产品交付路线已于2026-11-10更新为F安装分发、G完整工作流harness接入、H评测与开源首发准备，详见[路线与验收](open-source-harness-roadmap.md)。阶段任务更新不表示已经公开发布或具备任意宿主兼容性。
