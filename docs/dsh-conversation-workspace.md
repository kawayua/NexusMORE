## 四项验收与边界

| 任务 | 本次完成 | 验证范围 |
|---|---|---|
| 会话与题目绑定 | 真正的 task_create 回执绑定；项目继承、不可换题、跨题变更拦截 | 单元测试 + 已安装 DSH Host ToolRuntime/MCP 工程调用；自然语言由真实供应商模型产生工具调用留待 G5 |
| 原生审阅与继续 | 沿用 G3 四轮全量审阅；新的模型批准提交后，核对最新绑定和 model_approved，再以稳定幂等键 resume 并 followup 当前 Agent | 原生退回、取消、缺少 M1 的批准拦截实测；获准后的唤醒分支用接口测试验证，不冒充已完成真实模型求解 |
| 旁边下一题 | 原生侧栏挂载独立 SessionProvider、输入框、问题卡和工具上下文；共用项目，使用新 task_id | 真实下一题按钮、两套原生输入框、子会话 pending 自动显示、跨题创建拒绝 |
| 恢复与发行 | 会话/项目及父子会话引用持久化；重开原会话恢复侧栏；刷新/切换不重复开标签；wheel/sdist 携带一致资源 | 原生 Host 全停再启动、浏览器刷新、切换回原会话及源码外安装检查；以本次验收报告为准 |

测试只使用 `a=2/3/4，求 x=a` 的工程题，不发送供应商模型请求、不运行求解器、不产出论文、不代用户确认。真实模型的自然语言建题、批准后生成代码与后续业务质量，属于后续 G5/H 验证；本报告不能证明这些已通过。

## 状态、继续与恢复

Python Workflow/PostgreSQL 是唯一业务状态源。`runs/host-bindings/dsh/` 仅存 session/project/task 和父子会话引用，不存业务阶段、决定、批准或回执副本，不修改任何旧任务或旧审批。父子记录只用于恢复页面导航，不把上题上下文和批准复制给下一题。右侧用独立原生会话，可通过宿主自带分栏/全屏调整宽度。

只对本轮新提交成功的 **model approve** 自动推进。宿主核对 project_id/task_id/version/contract_sha256 和批准已落库，调用带固定事件派生幂等键的 task_resume。后端返回成功且没有新待审项时，通过 DSH Agent.followup 发送 `cordis-host-runner` 来源的宿主通知，要求模型先读取 task_status 再做允许的工作。这条通知不是人类消息签名或新批准；继续仍受 M1/P1/P2/W1/W2 等后端门禁约束。

退回保持暂停，可继续在当前对话说明修改要求。取消、跳过、重放、未提交、结果不明或仍有待审项都不自动推进。结果、论文正文、配图等其他批准继续沿用原流程，不套用模型批准的自动 resume。最终确认后若断线，先点“查询原回执”，不要换键重发。查询只读，不能自动唤醒模型；需要继续时在同一会话发自然语言请求，模型必须读取当前状态。

重新打开原 DSH 会话可从宿主引用恢复下一题；不是新建任意会话就自动绑定旧题。未发送草稿的保存遵循 DSH 本身，本次未承诺草稿跨宿主重启保留。界面插件初始化异常会撤销已注册的可选界面并保留 DSH 使用及原 G3 命令；若按钮缺失应检查兼容基线和插件日志，不以重装或删除用户数据作为默认操作。

## 兼容与部署

本次基线为 Windows x86_64、DeepSeek Harness Desktop 0.2.2-rc.1、CPython 3.13.5；宿主 Node glue 与浏览器 JS 只承担接入，数据/数值/后端仍统一 Python。MCP 基础层保持 40 项模型工具，无审批 MCP 工具、无 HTTP 批准接口、无新监听端口。新浏览器资源依赖 DSH 原生 remotes/sidebar-right/conversation/session 及 React。

更新包后完整重启 DSH；普通关闭窗口可能只退到托盘。安装、回退和原生可信桥接见 [本地连接](dsh-local-connection.md)。安装器检查全部五个宿主文件与所选 Python 包中的哈希一致；这只证明安装身份，不代替宿主启动和业务验收。Windows MCP 在启动主线程预加载 NumPy，避免首次 task_create 在 AnyIO 工作线程加载科学 DLL 后已提交却无法返回；冷启动创建及重启幂等有专门回归。

本次工程用隔离 profile、隔离数据库和已安装的原生 Host，配合无可见窗口的 Edge 驱动 UI；不复制日常凭据，不更改 DSH 安装文件。正常环境另做启动及只读连接检查。测试输入均注明 TEST_SIMULATED_USER，不表示实际用户批准。详细证据与未测范围见 [G4.2 验收记录](release/dsh-conversation-workspace-20261116.json)。


## 2026-11-16 小题接入修复

点击“开始小题”在旁边打开原生小题会话，再直接输入题面；“继续下一题”沿用项目并创建新的任务与独立工作区。新会话的原生 shell 工作区位于用户本地数据目录下，每题独立；Python/MCP 的业务工作区不随之移动。旧会话保留其原工作区，不批量搬移或修改 ACL。默认 workspace-write 与宿主权限提示继续生效，禁止以关闭沙箱解决权限故障。

模型创建业务项目后，宿主仅从该会话实际接收的 user RPC 原文登记文本输入，由私有父进程绑定入口保存来源、冻结规范和哈希，再向模型交付 owner、artifact 与实读观测。模型或宿主通知文本不能伪装成该原文；不会向模型开放任意本机文件登记或业务批准工具。当前自动入口支持文本；附件不静默降级成文本，仍需可信附件导入。内置 `python -m modelcrew.workflow_mcp register-input` 是操作者回退入口，本次新原生文本题不依赖它。

新输入的内容寻址快照保留受支持的解析器后缀（例如 content.txt），旧 content 文件与冻结契约不改名。1.1.0 契约必须保留宿主 input_observation.observed 的实际观测；输入全文、来源哈希和字段语义分别处理，文档不能伪装成数组文件。

needs_user_input 仅表示有待办。自动或“审阅当前题”均须重新查询权威 host_review；数学基线、当前版本的独立 M1、输入实读和引用证据满足条件、且没有 open_questions 时才打开方案审阅。真缺失的信息走“补充题目信息”原生卡，回复只形成带版本的资料补充，后续重新建模/M1；取消、版本变化或旧回复不会产生批准。建模手只应询问影响模型有效性的未知事实，题面明示条件与方案批准不列为缺失问题；程序仍保留真实疑问，不自动删问题。

诊断入口 /nexusmore-sandbox-check 只在当前原生会话执行固定的 PowerShell 版本查询，不接收参数、不发送模型请求、不代替用户批准。首次 M1 后仍保持待审阅；真实用户方案/结果决定、代码手与完整 G5 故障矩阵继续分别验收。
