# DSH 原生对话审阅

**当前使用入口（2026-11-19）**：[使用指南](user-guide.md)与[兼容范围](compatibility.md)汇总当前操作；G已按既有本地DSH实测范围验收，干净设备按用户决定在开源后补测。本页下方带日期的实施/验收段落保留历史时点含义，正文与配图的当前交互以合并审阅规则为准。


2026-11-16：默认入口改为“回复附待审文件 → 结束本轮 → 用户在原生输入框回复”。继续使用 DSH 原生聊天、原生 Markdown 文件预览和原生侧栏；没有新增聊天页面或批准 HTTP 接口。旧的 `/nexusmore-review` 问答入口保留作诊断回退，默认自动流程和“审阅当前题”不再打开完整 JSON 弹窗。

准备就绪后，宿主通过私有父进程入口读取当前完整审阅快照，生成新的待审 Markdown。回复展示 `dsh-resource://file/session/...` 原生链接，用户点击后在原生文件侧栏查看。后台保留待办，等待期间不轮询、不保持问答进程、不产生授权事件；重新启动不使文件自行失效。文件、快照和版本变化后必须重新展示并再次确认。

用户对单一待审稿回复“通过”“审核通过”“确认通过”“确认审核”“确认当前版本”“确认当前版本，继续”“确认这个版本，继续”或“通过，继续”时，宿主捕获当轮真实用户 RPC 消息。末尾句号或感叹号不影响确认。否定、疑问、引用、条件和混合修改意见（例如“通过，但先修改第二条”）不构成批准；普通意见继续交给当前模型讨论、修改并按影响重新审查。任何讨论回复都会撤销旧稿的快捷确认入口，待当前稿再次展示后才能确认。

DSH `agent/pre-step.messages` 只有当步新领取的输入，不是聊天历史。桥接先持久化发布文件通知，再在该通知进入原生 Agent 步骤后接收后续新用户消息；与通知同批的输入不能批准。模型回复、宿主通知、无用户 RPC 身份的文字和附件不会被当成用户签字。确认原文同时保留为决定陈述及理由，不代用户编写理由。原生会话、RPC/消息身份、完整审阅哈希、Markdown 哈希及具体业务绑定独立写入原有可信捕获账本。

2026-11-18 用户更新：同一写作运行的正文与配图同时待审时，直接展示合并审阅页，包含完整正文和所有候选图的实际图片；一次明确“通过”或“确认”同时记录当前正文及暂列配图批准。其他不同任务或版本仍需确定目标，不跨范围合并。独立 M1/P1/P2/W1/W2、数学、输入、全页图文检查和既有业务阶段门槛没有因为界面简化而豁免。当前实现不把这些独立质检节点改成人工签字节点。

提交前重新读取当前待办和完整证据，在同一业务锁下比较显示时的快照和当前版本。仅有正确 JSON、模型工具参数或普通 shell 不能生成可信决定；私有入口仍要求 Windows DSH 父进程、匿名管道、Python 3.13 及安装适配器身份。模型可见 MCP 仍是原来的 40 个业务工具。一次消息最多捕获一笔；重复回调不重新提交，断线或结果未知时先查询原回执，不能换键重发。模型批准后沿用现有受版本核验的后端续接，不把批准等同于求解或结果通过。

实现入口为 `modelcrew.dsh_chat`、`resources/harness/nexusmore-dsh-conversation.mjs` 和 `resources/harness/nexusmore-dsh-decisions.mjs`。历史冻结任务、旧批准、原有 G3 捕获和旧验收记录不改写。当前真实 G5 会话已由用户先前批准模型、处于代码流程；此次界面工程不替用户补签、不推进该任务，也不宣称完整 G5 验收完成。

工程验收：Python 210 项、JavaScript 68 项通过；真实 DSH 回复中的文件链接已点击并在原生 Markdown 侧栏实际读取，且无问答卡。wheel、sdist、重建 wheel 和源码目录外安装资源检查通过。用户文字确认只在隔离数据库执行合成测试，没有代用户提交真实批准。78 份既有验收/冻结契约文件及当前真实 G5 任务状态保持不变；详见[本批工程记录](release/dsh-chat-review-20261116.json)。

## 原生展示与完整确认语句修补（2026-11-16）

宿主读取 MCP 的原始 structuredContent（DSH ToolResult.value），不依赖可能截断或改写的模型展示文本；旧文本回执保留兼容。自动发布遇到繁忙时保留最新待审请求，只有成功发布才登记去重；发布失败向模型明确报告，不能把自行附上的 Markdown 当成已登记审阅。恢复会话若没有宿主待审记录，下一条真实用户消息先触发当前版本核对和正式文件展示，该条消息不追溯成为新文件的批准。文件通知必须已进入一个原生步骤，之后的新用户回复才能确认。

除既有简短确认外，模型方案支持整句“同意建模方案”“通过建模方案，进入代码手”“确认你的三个口径 通过建模方案 进入代码手”等有限语法。Python 可信捕获和宿主 JavaScript 同时检查整句，并绑定 model 审阅对象；这些模型专用语句不能批准结果、正文或配图。不采用含“通过”即批准的关键词匹配；否定、条件、疑问、引用、混合修改、跨对象批准或多行指令仍不授权。确认原文保留在事件陈述和理由中，现有版本/快照/文件哈希、独立 M1、一次性捕获和重复请求检查继续执行。

源码与打包资源同步更新后，已运行的 DSH 需完整重启加载。真实 G5 的旧确认消息不补签；当前 v2 在新宿主正式展示后，仍等待用户新的明确确认。本批工程测试不代替真实用户批准或完整 G5 业务验收。

## 建模待审稿的可读正文与证据附件（2026-11-16）

建模待审稿改用 `readable-model/1`：先展示问题目标和当前版本独立 M1 对应的建模说明，再展示假设、参数、检验要求、候选图计划、输出口径及本次确认范围。说明来自已有产物，不新增模型调用或编造推导/结果；没有可引用正文时按当前契约说明求解安排，并明确标注正文缺失。完整契约、数学包、输入结构、来源原文和审计记录另存为不可变 JSON 证据附件，正文保留原生文件链接，不能因精简正文而丢失批准对象的证据。

新版进入原会话目录下新的 `readable-model-v1/` 子目录，文档、证据和原建模说明哈希共同绑定展示身份。旧文件、旧捕获和历史通过记录不覆盖、不改哈希；旧捕获继续按原身份校验。说明原文、正文或附件发生改变时，旧展示拒绝确认，新内容生成新的展示身份。宿主检测到仍指向旧机器字段稿时，先发布并展示新版；触发换版的那条用户消息不补记为对新版的批准。

这是模型方案的审阅展示修补，不是正式论文写作或数学方案变更，也没有代用户确认。真实 DSH 仍需加载更新后的宿主模块，当前版本正式展示之后的新确认才可提交。

## 结果待审稿的可读呈现（2026-11-18）

结果页新增readable-result/1独立呈现器，与已有readable-model/1分开版本化。可信审阅读取已登记执行的逻辑文件索引，并重新核验当前独立P2/全页视觉回执和用户误差接受记录；只读取哈希匹配的注册原件。正文优先显示主要数值、七时刻表格、原要求与接受偏差、中文检查状态、三幅代表图、Excel及候选图链接。完整原始review和来源索引写入证据附件，不再把数据库树或CAS列表当正文。

为使用户能打开文件，呈现包提供保留原字节的同名带扩展名副本，逐一核验哈希，不能替换正式产物。每次确认重验原件、展示副本和证据附件；源数据、图片、稿件或附件变更均拒绝旧确认。新稿写到readable-result-v1新目录，独立preview身份绑定renderer/Markdown/证据哈希；旧字段树审阅、旧模型稿和历史批准不改写。原生聊天桥每次新建Python子进程加载当前呈现代码，回原对话请求“重新展示当前结果审阅稿”即可刷新，通常无需重启MCP或重跑计算/P2。


## 合并审阅的可信提交（2026-11-18）

新增readable-paper-bundle/1呈现器，原件保持字节不变，带扩展名的展示副本与原件逐一核验。正文图片链接映射到本次已注册的展示图片；清单展示全部候选图、类别、用途、拟放章节及PNG/PDF/SVG链接，并明确正式暂选与备选。原生“审阅当前题”默认生成合并预览，不再先选正文或配图。原choose_required记录中的“看图”或“确认”只触发展示，不能追溯批准尚未展示的合并稿；需在通知送达后等待新的真实用户消息。

合并待办以正文和图目录的哈希摘要共同绑定，原生私有hand_decide请求通过approve_figures及两个组件哈希明确范围。HTTP旧HandDecision及冻结契约文件保持不变。记录两类决定前先校验两者完整内容；两项批准、幂等摘要与组合证据在同一业务状态保存中生效。历史单项记录不覆盖。重复原生消息不再捕获或提交；任一原件、展示图片或证据变更拒绝旧预览。最终导出和独立终检仍执行。

宿主JavaScript和随包副本同步更新后，运行中的DSH需重新加载宿主模块；仅重连MCP不会加载该JS修改。本次工程验证使用隔离数据库的合成用户与合成供应商，不替真实用户批准。


2026-11-18 补充：明确的单句“同意”与“确认”“通过”一致，按实际展示对象捕获；否定、引用、疑问、条件、混合修改仍不批准。此前未识别的“同意”被记录为discussion时，不补签旧消息，先点击“审阅当前题”重新展示，再等待新的真实确认。已运行旧宿主可直接用已支持的“通过”，无需为此次确认再次重启。


## 汇编待审路由与合并确认（2026-11-18）

原小题的正文/配图已批准后，该task的pending为空不代表项目没有待办。审阅按钮先查当前task；无待办时只寻找同项目、冻结章节确实引用该task（指定run时也须匹配）、source_ready且当前有效的待审汇编构建。唯一匹配时把审阅投向该build；不同任务不路由，多个匹配要求明确选择，不盲选最新。原会话task绑定保持不变，不以修改旧绑定或业务状态实现切换。

同一build的正文与配图可合并为一个展示和一笔可信用户确认，保存两种范围的记录，在同一状态事务中生效。呈现器核验汇编原件、登记图片、目录证据与build对应关系，正文完整展示并附带全部候选图。捕获事件的scope绑定实际build；确认前重新核验该build仍引用原对话task及当前稿件哈希。保留旧手稿批准，不把旧消息补签到新汇编稿，不将“正文通过”这样仅指正文的文字扩大为两项批准。用户查看新合并页后回复“确认”“通过”或“同意”才提交。

这些变更位于每次启动的Python私有审阅进程内，已运行宿主可再次点击“审阅当前题”刷新，无需为路由修补重新启动DSH。模型MCP仍没有用户批准工具；汇编确认后只到READY_TO_EXPORT，正式导出、全页渲染检查和独立W2继续执行。
